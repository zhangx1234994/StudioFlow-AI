## 2026-04-16
- 问题：图片 provider 链路在多人排查时容易把 Coze submit、callback workflow 和状态回填混成一个问题，导致有人误以为“提交成功就应该立刻拿到图片”或“默认应走 task get 查询”。
  根因：缺少一份单独的图片 provider 真源文档；Coze 当前环境又恰好未配置 `SERVICE_API_TOKEN`，实际走的是 callback workflow 轮询，但这层事实没有被固定下来。
  修复：新增 `/Volumes/MAC 1/shipin/docs/image-provider-contract.md`，明确默认图片 provider 是 `coze`、当前环境依赖 callback workflow、KIE 仅是可选 fallback；并补充真实 live 验证结论。
  防护：后续图片链路排障必须先按 `submit -> provider_task_id -> callback -> 状态回填` 四段拆分，再决定是 provider 问题还是内部问题；禁止在未拆段前写“中台没走通”。

- 问题：商品棚拍、模特精修、多角度虽然都属于图片工具，但对象模型、确认门和默认主路径没有被统一收口，导致后续改造容易各自长出第二套语义。
  根因：历史工具文档按单工具分别记录，缺少一份“图片产品统一结构执行稿”，无法约束 Prompt、provider 和页面工作台的边界。
  修复：新增 `/Volumes/MAC 1/shipin/docs/plan/26-image-product-restructure.md`，统一三条图片线的产品定位、核心对象、确认门、Prompt 重点字段、provider 边界和实施顺序。
  防护：后续图片产品改造必须先引用 `26-image-product-restructure.md` 冻结对象模型与确认门，再进入代码实现或 UI 调整。

- 问题：商品棚拍工作台虽然已有 4 步框架，但 Step2 和 Step3 的产品职责边界仍然偏糊，导致方案确认、Prompt 编译、试拍和交付动作容易在同屏打架。
  根因：历史上为追求快速可用，把多个动作堆进同一阶段：Step2 同时承载方案编辑和执行确认，Step3 过早暴露了 Step4 的交付动作。
  修复：新增 `/Volumes/MAC 1/shipin/docs/plan/27-product-image-workspace-execution-spec.md`，明确 Step1~Step4 的页面目标、主 CTA、次级动作、状态反馈和代码落点。
  防护：后续商品棚拍工作台改动必须先对照 27 号执行稿，尤其检查 Step3 是否提前暴露交付动作、Step4 是否把手动微调降为次级入口。

## 2026-03-20
- 问题：前端 hasActiveAsyncTasks 将 queued_task_count 计入，导致 queued 状态被误认为"正在执行"
  根因：`hasActiveAsyncTasks` 检查了 `queued_task_count > 0`，使得排队中的任务也被视为活跃任务
  修复：从 `hasActiveAsyncTasks` 中移除 `queued_task_count` 检查，仅统计 running/rendering/backfilling
  防护：新增前端契约测试 `test_has_active_async_tasks_excludes_queued`

- 问题：前端 TASK_RISK_LABEL 缺少 queued 状态定义
  根因：任务风险等级只有 blocked/pending/running/other，没有单独的"排队中"状态
  修复：新增 `queued: "排队中"` 到 TASK_RISK_LABEL，并在 `resolveTaskRisk` 和 `taskNextActionHint` 中处理
  防护：新增前端契约测试 `test_task_risk_label_includes_queued_status` 和 `test_task_next_action_hint_handles_queued`

- 问题：资产页面 KPI 未区分"执行中"和"排队中"任务
  根因：`hubKpis.running` 将 running 和 queued 合并统计
  修复：分离 running 和 queued 计数，KPI 分别显示"执行中"和"排队中"
  防护：新增前端契约测试 `test_assets_page_kpi_separates_running_and_queued`

- 问题：批量任务统计把 reviewing 状态计入 queued_images
  根因：`_compute_batch_stats` 用 `total - done - failed` 计算 queued，导致 reviewing 被误计
  修复：reviewing 计入 done_images，queued_images 仅统计真正 running/queued 状态的任务
  防护：batch 统计逻辑已修正并有测试覆盖

- 问题：pipeline_service.py 过于臃肿（6400+ 行），难以维护
  根因：用户管理、计费、项目管理、图片/视频生成全在一个类中
  修复：拆分出 UserBillingService，创建 Repository 模式封装 store，创建 Provider 适配层接口
  防护：后续新增功能优先考虑拆分到独立模块

## 2026-03-19
- 问题：商品棚拍“任务中心 / 首页继续上次任务 / 资产中台任务卡”对同一任务的下一步提示口径不完全一致，用户会在不同入口看到不同引导。
  根因：部分页面直接使用前端 fallback 文案，未优先读取后端 `next_action`；回访卡片与任务卡演进不同步。
  修复：统一三处入口都优先展示后端 `next_action`，仅在缺失时回退前端提示；商品棚拍任务卡补齐风险/状态/交付进度/下一步的稳定主线。
  防护：在 AGENT_PLAYBOOK 增加硬规则：商品棚拍任务中心、回访卡、工作台摘要条必须共用同一套下一步口径，禁止跨页面冲突。

- 问题：商品棚拍 Step4 虽已具备批量动作，但异常候选与正常候选的主路径不够聚焦，用户容易直接在结果墙中混排误选。
  根因：Step4 顶部摘要、批量动作、异常候选与正常候选区之间缺少更明确的主路径提示和视觉分段。
  修复：Step4 增加批量主路径提示，固定“优先补拍异常 -> 一键入选剩余 -> 批量分享到首页/打包下载”的动作顺序，并把异常候选区与正常候选区显式分开。
  防护：在 AGENT_PLAYBOOK 增加硬规则：商品棚拍 Step4 必须异常优先、批量优先，手动微调只能作为次级入口。

- 问题：浏览器并行跳转时曾误判 `quick-video-15s` 串到了讲解视频页，容易把排查误差当成真实 bug。
  根因：同一 Playwright 页面并发导航导致观察结果互相覆盖，未先做顺序复核就形成结论。
  修复：顺序单独复查 `quick-video-15s`，确认当前页面渲染正常，本轮不对该工具做代码改动。
  防护：以后浏览器走查中遇到跨页串结果，必须先做一次顺序复核再写入问题结论，避免误追错问题。

## 2026-03-02
- 问题：点击创建任务报错（OSS签名缺字段）
  根因：`/api/v1/oss/sign` 返回缺少 `updated_at`，导致响应模型校验失败。
  修复：补齐 `updated_at` 字段。

- 问题：新建项目后找不到（OSS 异步持久化覆盖内存）
  根因：启用 OSS 异步持久化时，读取接口仍会从远端覆盖本地状态。
  修复：异步持久化时跳过远端 sync。
  防护：在 store 层增加“异步持久化禁止同步覆盖”规则。

- 问题：mock 模式下脚本为空导致脚本选择失败
  根因：intro bootstrapping 走异步导致 create 返回时 script_options 为空。
  修复：mock 模式同步执行 bootstrap。
  防护：mock 模式严格同步，保证测试用例稳定。

## 问题：本地 `store.json` 体积暴涨到 326MB

- 防护：以后凡是异步任务，必须保证“任务状态”和“资产终态”双向收敛，不能只依赖事件流单向推进。

## 问题：登录/工具首页首屏发生 hydration mismatch，页面看似卡住但后台并未真正发起业务调用
- 现象：用户第一次打开登录页或 `/app/tools` 时，页面可能卡在首屏不动，控制台出现 React hydration 错误，看起来像“能力中台没有收到调用”。

- 修复：`useRouterState` 统一改为稳定的 SSR 初始值，真实路由在 `useEffect` 中同步；登录页错误态也改为 hydration 后再读取 query 参数；同时补上登录/注册表单的 autocomplete，确保浏览器 smoke 控制台为 0 error。
- 防护：以后凡是会影响首屏结构、路由或状态文案的浏览器态（`window/location/search/sessionStorage/localStorage`），必须延后到 effect，同步后再更新 UI；交付前必须做登录页和工具首页的 Playwright console 检查。

## 问题：前端模块抽离后出现多处漏 import，`build` 通过但真实页面仍会白屏
- 现象：`/app/tools`、`/app/assets` 等页面在真实浏览器中出现 `VISIBLE_TOOL_LIST / TASK_RISK_LABEL / formatProgressLabel` 等未定义错误，而 Python 测试和 `next build` 仍然通过。

- 防护：以后凡是做前端大规模抽离/搬运，必须在交付前同时完成三件事：关键页面浏览器烟测、console 0 error、运行时未定义变量扫描；仅凭 `build` 通过不得交付。

## 问题：工具入口按钮可能“看起来可点”，但实际 URL 未被主页面路由分支接住

## 问题：工作台提示词偏好字段写进表单了，但没有真正进入规划与最终提示词编译
- 现象：用户在工作台填写 `goal / style / shot_focus / constraints` 后，生成结果对这些偏好响应很弱；其中 `goal` 基本未生效，`shot_focus` 还会错误覆盖 `brief.evidence_points`。

## 问题：单图生图请求仍沿用多图 schema，导致无辅图时也传了辅图字段

- 修复：请求 schema 改成分层组装：主图只走 `url`；仅当辅图真实存在时才传 `image_urls`。
- 防护：以后凡是 provider 接口存在“必传主图 + 可选辅图”的场景，必须在组装层做条件分支，禁止把单图请求包装成多图请求。

## 问题：用户已选择比例，但最终 provider 请求没有稳定落到真实宽高
- 现象：前端切换了比例，后台仍可能只看到抽象比例或默认值，没有收到该比例对应的 `width/height`。
- 根因：比例到宽高的换算函数虽然存在，但没有稳定落到最终商业模型请求 payload，导致“算出来”和“真正发送出去”脱节。

## 问题：商品棚拍异步试拍数量可能被历史默认值放大，前台等待感被放大
- 现象：前台当前选择了较小试拍数量，但后台实际生成数量明显更多；同时前台状态又迟迟不像真正开始，用户体感就是“后台跑很多、前台没更新”。

- 修复：商品棚拍实际生成数量改为优先按当前请求值执行；异步提交后立即把项目标记为 `running`。
- 防护：以后凡是“创建期默认值”和“运行期即时选择”同时存在的字段，运行期值必须优先；异步提交后必须立即回写运行态，禁止让前台进入“像没开始”的灰区。

## 问题：商品棚拍提示词结构缺少显式参考图角色声明，风格参考可能稀释主体真源
- 现象：虽然商品棚拍已经有主体参考板，但最终生图提示词里没有强制写清“图1是主体真源、其余图只做风格/细节参考”，模型仍可能把附加参考图当成主体定义的一部分。

## 问题：前端 OSS 直传失败后曾自动回退到服务端文件上传，导致创建链路继续双轨运行
- 现象：浏览器在 OSS 直传报错后，会自动改走 multipart 服务端上传；后端创建接口也继续接受二进制文件，结果“前端直传 OSS、后端只接 URL”只停留在文档，生产链路仍可能悄悄回退。
- 根因：前端为了“先让功能过得去”保留了服务器上传兜底；后端也没有在 OSS 已启用环境下做硬拒绝，导致旧路径长期存活。
- 修复：前端创建页移除“自动切换服务器上传”逻辑；后端在 OSS 已启用环境下拒绝 `POST /api/v1/projects` 与 `POST /api/v1/tools/model_retouch/batch-create` 的二进制文件上传，要求先调用 `/api/v1/oss/sign` 再提交 `*_public_url`。
- 防护：以后凡是文档声明“后端只接 URL”的上传链路，都必须同时具备三项：前端无文件回退、后端有硬门禁、测试覆盖“OSS 启用时拒绝二进制上传”。

## 问题：模特批量工作台 stepper 曾允许直接跳到执行/审核步骤，和门禁规则不一致

- 防护：以后所有 stepper 都必须同时满足三项：可点击直达、点击前做前置校验、自动步骤同步只能纠偏非法状态，不能覆盖用户主动切换。

## 问题：批量工作台的 stepper 阻断提示曾混在顶部汇总状态里，浏览器回归不稳定
- 现象：点击被门禁阻断的 Step3/Step4 后，页面虽然没有真正跳步，但阻断提示和批次汇总状态共用同一 banner，容易被刷新/其他状态覆盖，浏览器走查时不够稳定清晰。

## 问题：单项目工作台的 stepper 阻断提示也曾复用 action 状态，和业务提示串线
- 现象：商品棚拍等单项目工作台点击被门禁阻断的步骤时，提示会写进 `actionStatus`；这会和“方案已就绪 / 生成中 / 下载成功”等业务提示混在一起，用户不容易分辨是导航阻断还是执行反馈。

- 防护：以后工作台内至少区分两类提示通道：步骤导航阻断提示、业务动作结果提示；二者禁止混用同一状态源。

- 现象：在商品主体锁定步骤里，页面顶部和主体选择区都会出现“确认使用当前选择并进入方案”这类主按钮，用户会感知到两个同权主动作。

## 问题：矩阵自测脚本曾把上传源图 / product-lock 资产误算进“已生成张数”
- 现象：脚本报告里 `generated_assets/generated_ready_assets` 会比真实成片数多 1~2 张，`expected_ready_assets` 也会偏大，导致 9x3 这类场景被误判成“还没生成完”或统计口径混乱。
- 根因：脚本直接按 `/assets` 全量列表和全部 generation tasks 计数，没有把 `uploaded input`、`generated input(product-lock)` 与真正的 `generated_image` 区分开；同时默认假设 `takes_per_shot` 会直接放大 image generation 任务数。
- 修复：矩阵脚本改为只统计 `source_type=generated && kind=generated_image` 的资产，以及 `task_type=image_generation` 的任务；预期成片数优先按真实 image task 数计算，不再把 product-lock/source 资产混进结果数。
- 防护：以后所有端到端自测报告都必须先冻结统计口径，再下结论；涉及“生成张数/失败张数”时必须显式写清 asset/task 过滤条件。

## 问题：Coze callback 轮询降频后，慢任务仍可能因超时过短而被误判失败
- 现象：为了减少 callback workflow 记录数量，轮询间隔从 5s 拉长后，部分 9 张图场景里的慢任务会在结果真正回来前先被打成 fallback/failed，造成“8/9 成功”的假失败。
- 根因：只做了“降频”，没有同步把远端 callback timeout 拉长；慢任务总等待窗口仍不足。
- 修复：远端 Coze callback 轮询统一改为 `12s` 间隔 + `300s` 最短超时，本地环境仍保持短轮询；回归验证后 `commercial_9x1_plan` 从 8/9 提升为 9/9。
- 防护：以后所有“为减压而调低轮询频率”的改动，都必须同步校验等待窗口是否覆盖最慢任务时长，并至少复跑一条高并发真链路。

## 问题：商品棚拍生成阶段曾复用泛化“生成中”文案，用户感知不到当前是在试拍候选图
- 现象：商品棚拍在 Step3 明明是在“试拍候选图”，但按钮和状态条文案仍写成“生成中/提交生成任务”，用户难以理解当前会逐张回填候选图，也不清楚为什么要先试拍再选片。

- 修复：商品棚拍 Step3 改成专用文案：`正在提交试拍任务`、`已开始试拍，候选图会逐张出现并自动刷新`、按钮执行中显示 `试拍中...`。
- 防护：以后工作台的状态文案必须优先使用工具语义（试拍/精修/机位生成/视频候选），禁止所有工具都复用一套抽象“生成中”。

## 问题：商品棚拍失败重试曾可能丢失用户上一次真实试拍参数

- 防护：以后所有带“运行时可选参数”的生成链路，只要提供 retry，就必须优先复用最后一次真实提交参数，禁止悄悄回落到项目默认值。

## 问题：配置层把 Coze workflow id 写成代码默认值，导致环境配置失效

- 现象：
  - 顶栏已经换成统一壳层后，任务中心、资产页等页面顶部仍单独出现一行 `首页 / ...` 路径文字，视觉上仍像旧后台。
- 原因：
  - 页面结构迁移到了新壳层，但 `page.jsx` 还保留了旧 breadcrumb 输出。
- 处理：
  - 移除常规页面内容区顶部的 breadcrumb 行，让页面层级由 hero 和内容卡自身承担。
- 防护：
  - 以后全局壳层改造时，必须逐页检查顶栏下方是否还残留独立路径行；只要还存在，就不能判定静态稿风格收口完成。

## 2026-04-16 任务中心概览指标只保留一层

- 现象：
  - 任务中心 hero 已经展示“卡住 / 待确认 / 执行中 / 总任务”，列表区再重复一组 chips，会让页面再次变成看板。
- 原因：
  - 为了“信息完整”保留了重复概览，没有把 hero 视为唯一摘要层。
- 处理：
  - 保留 hero 概览，移除列表区重复 chips，只保留筛选条和优先队列。
- 防护：
  - 以后任何页面如果已有首屏摘要层，列表区不得再重复同一组指标；同一语义只能出现一次。

## 2026-04-17 商品棚拍工作台按钮必须回到全局体系

- 现象：
  - 首页和任务中心按钮已经进入统一深色金棕语法，但商品棚拍工作台仍保留一套内联 `gold/dark` 按钮，视觉上像另一个主题。
- 原因：
  - 工作台早期为快速验证交互，直接写了内联按钮色值，后续没有随着全局按钮体系一并收口。
- 处理：
  - 把商品棚拍 Step3/Step4 主动作、筛选按钮、右栏导航改回全局 `btn-primary / btn-secondary / btn-ghost`，只保留尺寸辅助类。
- 防护：
  - 以后专用工作台允许扩展布局和尺寸，但不允许再独立维护一整套按钮颜色；按钮语义必须复用全局主/次/弱动作体系。
