# Agent 工作准则（持续更新）

> 目标：少犯重复错误、提升交付质量、持续复盘改进。

## 1. 核心原则
- **不重复犯错**：错误必须记录、归因、形成可执行的防护措施。
- **举一反三**：发现 1 个问题时，必须主动排查同类页面、同类接口、同类状态机与同类配置，不得只修单点表象。
- **一次交付可验证**：每次提交必须附验证结果（ruff/pytest/关键流程）。
- **先设计后实现**：交互/流程变更先写清楚再动代码。
- **状态可见**：任何异步动作必须有明确 UI 状态。
- **用户不做首轮排错**：问题必须先在本地复现并修复，再交付用户验证。
- **文档同步**：接口/交互/流程变更必须同步更新文档索引与对应规范。
- **首屏一致性**：客户端页面首屏必须保证 SSR 与 hydration 初始状态一致，禁止直接用浏览器对象参与首屏状态分支。

## 2. 必做清单（每次交付）
- [ ] 运行 `ruff` + `pytest`
- [ ] 核心流程 smoke（创建→方案→生成→结果）
- [ ] 交付给用户测试前，先由 agent 自己完成页面走查（至少覆盖登录页、首页/工具箱、改动页面、关键按钮可点击性）
- [ ] 对高风险功能完成参数矩阵自测（至少覆盖不同 provider / 比例 / 数量 / 是否带参考图 等关键组合），不能只验证 1 条主链路
- [ ] 页面可导航回 `/app/tools`
- [ ] 图片/视频表单不互相混用
- [ ] OSS 直传可用：`/api/v1/oss/sign` 返回 200 + 字段齐全
- [ ] 上传不阻塞创建：创建后立即进入工作台
- [ ] “主操作”唯一，辅助操作收起
- [ ] 交互/视觉调整使用 UI/UX Pro Max 技能完成评审与输出
- [ ] 走查使用 Playwright CLI 技能执行并记录结果
- [ ] 首屏页面浏览器 console 为 0 error，尤其排除 hydration/render mismatch

## 3. 常见错误防护（更新区）
- OSS 直传签名返回字段完整性（含 `updated_at`）
- 任务创建不应被上传阻塞（先跳工作台）
- OSS 已启用环境下，前端创建流程禁止自动回退到服务端文件上传；若直传失败，必须直接暴露错误并阻断创建
- Mock 模式下异步任务要同步完成（测试稳定）
- OSS 异步持久化不得覆盖内存（避免新建项目丢失）
- 文件选择按钮必须可点击（`label + input` 方案）
- 前端不得暴露 JSON 直改，用户只编辑可读表单
- 方案生成必须异步提交（`/plan async_mode=true`）并轮询进度，禁止前端长请求卡死
- 生图/生视频统一采用“提交任务 -> 后端集中轮询 -> 状态回填”的任务服务模式；禁止在页面组件里各自散写 provider 轮询逻辑。
- 图片 provider 默认路由真源固定为 `coze`；若当前环境未配置 `SERVICE_API_TOKEN`，则 Coze 图片结果回收必须走 callback workflow，禁止把 callback 视为可选能力。
- Coze 图片链路排障必须拆成四段：`submit -> provider_task_id -> callback workflow -> 状态回填`；禁止在未拆段前笼统下结论为“中台没走通”。
- 图片产品改造必须先对齐三条线的对象模型和确认门：
  - 商品棚拍：主体锁定 / 方案 / Prompt / 候选图
  - 模特精修：身份锚点 / 精修指令 / 结果候选
  - 多角度：机位草稿 / 角度候选
- 未冻结对象模型和确认门前，禁止直接扩图片工具字段或随意新增主 CTA。
- 商品棚拍工作台收口时，Step3 不得提前平权展示交付动作；`一键入选 / 批量分享 / 打包下载 / 手动微调` 应以下沉到 Step4 为默认准则。
- 刷新后若仍在方案阶段运行，主 CTA 保持禁用并展示“方案生成中”
- 状态文案统一中文（提交中/执行中/成功/失败），禁止英文前缀混用
- Step 1 页面保持单主动作，不出现并列主流程按钮造成决策干扰
- 工作台步骤导航固定为顶部横向进度条，禁止回退到页面左侧步骤栏挤占主操作区
- 首屏核心区（工具卡/步骤头/KPI/任务卡）必须图文并茂（矢量图标 + 精简文案），禁止大段纯文字堆叠
- UI 评审标准从“可用”升级到“可商用”：字体、背景氛围、卡片层级、按钮反馈需统一并体现高级感
- 登录页必须同时具备品牌主张、样片预览、能力摘要和明确登录收益，禁止退回成“单卡片表单页”
- 首页 Hero 必须同时承载品牌主张、主 CTA、运营样片预览和核心经营指标，禁止只剩标题+两个按钮
- 资产中台 Hero 必须同时承载操作入口、运营样片预览和资产 KPI，不得退化为“标题 + tab + 刷新按钮”
- 工作台顶部必须采用“步骤进度 + 状态摘要 + 下一步建议”三层结构，并维持统一的暖金/雾蓝卡片语义
- 工作台结果墙必须包含“结果说明 + 筛选器 + 统计卡 + 交付动作”四件套，禁止只剩素材平铺列表
- 桌面端工作台生成阶段必须优先采用“主控制区 + 侧边摘要区”双区布局，避免参数、统计、动作全部挤在一行
- 创建页表单必须采用“字段卡片化 + 说明文案 + 单主 CTA”结构，禁止回退成裸表单堆叠
- 五个工坊创建页必须存在场景差异化视觉层（头图/基调文案/能力 badge），禁止同一套头图与文案横向复用
- 工具卡、空状态、状态 banner 必须共享统一卡片语言（圆角、暖金/雾蓝边框、轻阴影），避免页面间视觉断层
- 任务卡、结果卡、工具卡内部必须采用“kicker/标题/状态或下一步/动作区”四层结构，禁止按钮直接贴在图片下方无信息缓冲
- 首页任务看板与资产中台任务列表优先使用任务卡，不优先使用表格；只有对账类信息才允许首屏表格化
- 日志抽屉必须降级为诊断层，不得在主视觉上抢占结果墙和生成控制台
- 顶栏必须采用“品牌识别 + 全局导航 + 快速搜索 + 账号状态”四段式结构，避免信息全挤成一排按钮
- 首页样片区必须采用“主打样片 + 次级样片网格 + 直接行动按钮”的运营结构，禁止纯平铺列表
- 工作台每个 Step 卡片必须包含统一抬头（STEP 标签 + 标题图标）与摘要信息条（阶段/进度/状态/下一步）
- 生成与审核步骤必须先展示控制台/摘要看板，再展示结果墙，避免用户直接落入密集素材列表
- 结果墙必须提供状态筛选（全部/已通过/待筛选/异常），大批量素材场景禁止只给单一长列表
- 运行日志必须降级为低优先级入口（默认收起 + 抽屉式查看），禁止长期占据主操作区
- 首页运营区必须同时提供“套图商品包”与“近期热销”信号位，保障运营导流和商业决策可见
- `queued` 仅表示待执行，不等于“执行中”；前端禁止把 `queued + 无plan` 渲染为“方案生成中”
- 前端 `hasActiveAsyncTasks` 不应包含 `queued_task_count`；仅统计 running/rendering/backfilling
- 前端 `TASK_RISK_LABEL` 必须包含 `queued: "排队中"`，并在 `resolveTaskRisk` 和 `taskNextActionHint` 中处理
- 资产页面 KPI 必须分离“执行中”（running）和“排队中”（queued），禁止合并统计
- 批量任务统计中 `reviewing` 状态必须计入完成侧（done_images），仅将真正 running/queued 计入排队侧
- 方案生成必须具备超时兜底（默认2分钟）：超时后自动解锁主 CTA 并提示可重试
- `delivery_purpose` 属于方案必填字段：解析层、保存层、读取层都要做非空兜底，禁止页面出现空用途
- 商品棚拍结果卡必须包含可读运营文案（非“字段拼接式”），且生成结果 metadata 需保留该文案字段
- 首页样片墙只展示“主动分享”素材：禁止自动把全部生成结果灌入首页
- 分享积分必须可控：仅已入选生成图可分享，且要有每项目/每日上限防刷
- 登录名规范化：会话中若存的是邮箱，后端必须映射回标准 `username`，避免出现“已登录但角色/积分为空”
- `/api/v1/auth/me` 必须返回统一字段：`authenticated/username/role/points_balance`，前端不得自行猜测用户身份
- 计费扣分必须“先校验余额、后按成功产物扣费”，禁止按计划数量直接预扣导致误扣
- 涉及 `project_id` 的接口必须执行 RBAC 校验（admin/operator 全量，member 仅本人），禁止仅靠前端隐藏按钮
- `MASTER_TODO` 任意勾选状态变更后，必须同步刷新顶部“已完成/未完成”统计，禁止手填过期计数
- 支付/充值相关能力必须走 feature flag；未接网关前默认关闭用户端充值入口，仅保留管理员手动调分
- `MASTER_TODO` 条目从未完成改为完成时，必须在 `docs/plan/*` 写明对应冻结决策（含 v1/v1.1 边界）
- 认证链路改动必须包含：注册路径、登录风控（账号锁定/IP限流）、`auth/me` 字段回归（role/account_status/workspace/points）
- 运营闭环需求（样片墙、拍同款、质量评测、prompt评测）必须先提供后端 API 真源，再接前端交互
- 图片生成回退图（`metadata.source=original`）在生产模式下必须标记 `failed`，禁止按成功资产展示或扣费
- 本地持久化默认使用异步写盘（`MVP_STORE_ASYNC_PERSIST=true`），禁止在高频交互动作中同步全量序列化阻塞主链路
- 本地启动统一使用 `./scripts/dev_service.sh`，禁止用一次性 `nohup` 交付（会导致会话断开后进程被回收）
- 服务器发布统一使用 `systemd` 托管，必须启用 `Restart=always`，禁止手工后台跑 uvicorn
- 模特精修 Step2 主 CTA 必须置顶（生成/确认），禁止下沉到底部导致用户找不到下一步
- 批次任务卡必须区分 `当前查看` 与 `查看该图`，当前卡按钮禁用，避免“点击无变化”误判为故障
- 模特精修执行口径固定为“单任务单图产出”；方案中的修正项只做指令约束，不直接映射为产物数量
- 模特精修交互顺序固定为“先模特确认，再单图精修”；创建后默认落到身份确认步骤，不得要求用户先浏览批次要求页
- 图像/视频提示词必须走结构化编译模板（image: 主体/镜头/目标/用途/...；video: Subject/Shot/Intent/...），禁止自由散文式拼接
- 只要图模型输入包含 2 张及以上图片，提示词必须显式声明 `图1/图2/图3+` 的角色（主图/锚点图/风格参考图）；禁止只靠顺序让模型自行猜测
- `derive-prompts` 后必须产出提示词质量评分（`image_prompt_quality_avg` / `video_prompt_quality_avg`），作为可执行性检查项
- 模特精修创建后必须跳转批量工作台路由 `/app/tools/model-retouch/batches/{batch_group_id}`，不得默认落到单项目页
- 上传替换模特图也必须先处于 `identity_status=pending`，只有显式“确认锚点”后才允许批量执行
- 模特精修默认策略固定为 `keep_original + original + light`；`output_aspect_ratio=original` 必须映射为生图参数 `image_aspect_ratio=auto`
- 模特精修参考图顺序必须固定：主图作为基底输入，身份锚点作为首个参考输入，风格参考图只能排在其后，禁止让模型自行猜测身份图
- 模特锚点页必须明确表达“两阶段任务”：先定模特本人，再批量替换整组套图；默认推荐全身标准照式模特图
- 模特工坊异常结果必须在 Step3 和 Step4 同时显式提示，禁止只靠小 badge 让用户自己猜“是否命中锚点”
- OSS 直传签名中 `role=source` 必须生成唯一 object key，禁止同批次多图覆盖到同一 URL（会导致“9张都显示成同一张”）
- 模特工坊所有入口（任务列表、旧链接、搜索跳转）必须统一落到批量路由 `/app/tools/model-retouch/batches/{batch_group_id}`，禁止再暴露单项目工作台主入口
- 模特精修 Step2 必须明确三选一主动作（使用上传/精修上传/生成新模特），禁止只给“生成候选”泛化按钮
- 模特精修 Step2 必须支持“替换已上传模特图”，且替换后仍需显式确认锚点；不可自动跳过确认
- 模特精修 `use_uploaded/beautify_uploaded` 必须显式绑定“最新有效上传模特图”，禁止读取可能已切到生成候选的 `identity_asset_id` 作为上传来源
- 模特精修 Step2 必须在同页展示“创建页带入素材 + 上传模特预览 + 替换 + X移除 + 生成新模特”统一面板，禁止把关键动作拆散到多页面
- 模特精修移除上传模特图后，系统状态必须立即回到 `identity_status=pending`，并要求用户重新确认锚点后才能执行批量精修
- 任何禁用按钮必须给出可见原因（如“未上传模特图，无法使用该动作”），禁止用户感知为“点击无响应”
- 图片生成比例必须可选且默认“原图比例”；UI 显示“原图（默认）”，后端统一映射为 `image_aspect_ratio=auto`
- 当选择“原图（默认）”时，分辨率控件必须禁用，且请求中不传 `image_resolution`（禁止隐式回落固定 1K）
- 15秒短片创建页必须收敛为 5 个视频核心参数（主题/节奏/语气/CTA/时长），禁止暴露图片工坊字段（目标成片数、每镜头试拍、机位参数）
- 15秒短片提交前必须做语义映射（主题/节奏/语气/CTA -> `key_features/tone/cta_text/scene_goals`），避免后端收到空泛默认值
- 工作台步骤区的次级动作（重新生成/保存偏好/生成执行方案）必须保持 `btn-secondary`，避免与主 CTA 同权竞争
- 工作台在尚无方案/脚本/候选时，只允许展示单一主 CTA；“重新生成/执行方案”类辅助动作必须在已有内容后才出现
- 模特工坊 Step4 必须提供显式导出入口；当存在已通过结果时，主 CTA 固定为“打包下载已通过结果”
- 多角度工坊的状态文案必须与主按钮动作一致：待执行提示只能引导“保存机位/开始生成当前角度”，禁止出现“生成机位方案”这类错位术语
- 视频工坊按钮文案必须与当前真实动作一致：讲解视频在编译 prompt 前不得写“进入视频生成”，15秒短片不得复用“拍摄方案”术语
- 账务回归至少覆盖一次“部分成功、部分失败”的生成场景，验证仅按成功产物扣费
- 商品棚拍规划必须透传执行提示（`expected_shot_count/takes_per_shot/target_candidate_assets`）；高镜头数默认走“先大纲后并发逐镜头”策略，禁止只依赖单次大 JSON 返回
- 若规划结果镜头数小于目标，必须触发缺失镜头并发补齐，不允许用同质化占位提示词直接凑数交付
- 商品棚拍若模型返回镜头数不足，后端必须先判定问题并至少重试模型一次；只有重试仍不足时才允许进入兜底补齐，禁止第一次不足就直接当成功交付
- 规划模型默认使用 `doubao-seed-2-0-pro-260215` 且关闭深度思考（`thinking=disabled`）；若修改模型档位，必须同时给出时延评估、账号可用性验证和回退方案
- VL 模型调用必须带候选回退链：当出现 `InvalidEndpointOrModel.NotFound` 时自动切换备用模型，禁止首选模型不可用时直接把 404 暴露给用户
- 商品棚拍结果页默认以“批量交付”动线为主（批量入选/批量分享/打包下载），单张按钮仅在手动模式展示，禁止默认满屏逐张操作按钮
- 参考图字段必须保留角色语义到服务层：主体参考、身份锚点、风格参考不得在入口层合并成同一列表，否则提示词角色声明会失真
- 用户可编辑的提示词偏好字段（如 `goal/style/shot_focus/constraints`）必须同时进入 planner、单镜头补全和最终 prompt 编译；禁止表单有字段但模型实际不消费
- Prompt 必须先过结构化质量门再进 provider；禁止把自由散文 prompt 或未标角色的多图输入直接交给生图/生视频模型
- 硬约束必须进入 schema 或 provider 参数，不能只写在 prompt 文本里“希望模型遵守”
- 单图请求不得伪装成多图请求：当没有辅图时，只允许传主图必填字段（如 `url`），禁止继续发送空的 `image_urls/reference_images` 一类字段
- 比例/分辨率类前端选择必须在最终 provider payload 中落成可验证的真实参数（如 `width/height`）；禁止只在中间层保存 `aspect_ratio` 却不进入最终请求
- 无辅图时，provider payload 中不得出现空的 `image_urls`；“主图 + 0 辅图”必须严格退化成单图 schema
- 运行期用户选择必须覆盖创建期默认值：例如商品棚拍当前 `candidates_per_prompt` 不得再被历史 `takes_per_shot` 放大
- 所有异步生成在提交成功后必须立即回写 `running` 态，禁止前台长时间停留在 `queued/像没开始` 的灰区
- 模特身份候选生成若改用上传模特图作为主输入，必须同时去重参考列表中的同一张图，禁止把同一图片同时作为主图和参考图提交给模型
- 讲解视频“生成”动作只能消费已确认的主脚本与分镜；前端禁止为了省步骤自动 select script / approve shot / confirm storyboard
- 生成素材落盘/持久化时必须显式传真实 `project_id`，禁止拿 `image_path.stem` 等派生值代替，否则多入口场景会把产物写进错误项目目录
- 创建接口的 `scenario_type` 不得信任前端裸传；后端必须按 `tool_type` 归一化或校验，避免工具错入错误工作流
- 创建页字段名必须与真实语义一致：风格参考图必须走 `style_reference_*`，禁止 UI 文案写“风格参考”却仍提交到通用 `reference_*`
- 同一业务能力的单项目接口与批量接口必须保持动作枚举一致；若批量支持 `use_uploaded`，单项目接口也必须同步支持或明确禁用
- 业务默认值必须与冻结文档一致；例如 15 秒短片默认候选数为 3，禁止前端/后端各自回落到 2
- Retry 逻辑不得回退到硬编码通用默认值；重试时必须优先复用该工具/项目当前配置（如商品棚拍 `takes_per_shot`、模特精修原图比例、短片候选数）
- 多角度工坊的前端控制范围必须与后端 schema 一致；如后端只允许 `pitch=-45~45`，前端 slider/预设/状态文案不得展示 `60` 等越界值
- 创建页隐藏字段若会进入请求体，必须绑定真实表单状态，禁止写死默认值冒充当前选择
- 各工坊阶段文案必须按工具语义映射，禁止把商品棚拍的“选片分享”等词复用到多角度/短片等其他工具
- 刷新恢复不仅要恢复当前 step，还要恢复当前 step 内的状态文案；禁止出现“阶段=生成中，但按钮区仍显示等待执行”的错位状态
- 同一业务流若同时存在“单项目工作台”和“批量工作台”，前端状态机、默认值、payload 构造必须抽成共享 helper/hook，禁止在同一文件里复制两份再各自演化

- Topbar 交互元素必须使用紧凑尺寸（小按钮/小芯片/短搜索），禁止把全局导航做成大 CTA 风格造成视觉拥挤
- Topbar 与首页文案必须是产品语言，禁止展示“状态码字段/工作空间ID”等开发语义
- 首页首屏 KPI 必须分层：核心指标卡优先，次级指标用 compact chips 展示，禁止全部指标同权重平铺
- 模特 Step2 必须采用“模式选择 + 单主动作”结构（使用上传/精修上传/生成新模特），禁止同时暴露多个并列主动作按钮

- 问题：失败项目点击“失败重试”后，虽然已经进入合法 retry 流程，但 `generate -> derive_prompts` 仍会再次被失败态保护拦截，导致页面继续收到 400。

- 问题：Coze workflow/run 在“工作流实际执行失败”场景下会返回 `debug_url` 和顶层 `msg`，但本地曾把这类失败统一落成 `IMAGE_GENERATION_FAILED / image generation failed`，导致排障时看不到真实的 NodeRunError。

- 问题：商品棚拍 Step3 的主区一旦同时出现筛选 Tabs、回工具类按钮、统计块和结果墙，页面会重新变成“后台控制台”，结果墙反而不是主角。

  修复：把“资产中台看进度”彻底收回右栏，删除 Step3 底部冗余统计块，主区只保留试拍相关动作和结果墙。
  防护：以后 Step3 任何新增动作都必须先过一道规则：如果它不是“发起试拍 / 重试 / 补拍失败项”，默认下沉到右栏或 Step4，不得占用主区首屏。

- 问题：商品棚拍 Step4 顶部如果只是标题 + 统计表格，虽然信息齐，但仍然像后台摘要，不像交付台。
  根因：交付阶段缺少“当前主路径”“优先级胶囊”“主动作/交付动作分区”这类真正帮助用户做判断的结构，只把数字堆出来了。
  修复：Step4 顶部改成“交付决策”块，明确区分当前主路径、优先级胶囊、交付进度和动作分区。
  防护：以后 Step4 顶部设计必须同时回答三件事：现在最优先做什么、当前候选池是什么状态、下一步动作归属哪一类；只给统计数字不算完成。

- 问题：用户强调“图从哪里来、谁控制”后，如果执行稿还只写交互，不写图片来源和控制边界，后续页面会继续混入静态样片与业务结果，或者把空态图当成真实结果。
  根因：之前对图片的设计只停留在展示层，没有把“主体原图 / 参考板 / 候选图 / 占位图 / 交付图”做显式分层。
  修复：在 `docs/plan/27-product-image-workspace-execution-spec.md` 增加“页面图片来源与控制边界”，逐类说明图片来源、控制者和空态规则。
  防护：以后任何带图片的工作台设计稿都必须显式标注图片分层与控制边界；未标明来源和控制者的图片，不得进入实现。

- 问题：商品棚拍 Step3 如果顶部仍是“标题 + 进度条 + 零散统计”的控制台写法，结果墙虽然在下面，但页面第一印象仍然不是工作台，而是后台监控面板。
  根因：Step3 之前只把生成信息堆在一个长条卡片里，没有像 Step4 那样明确“当前目标 + 回填进度 + 试拍动作”的结构层级。
  修复：把 Step3 顶部改成与 Step4 同语法的双栏决策块：左侧写“当前目标”，右侧写“回填进度”，底部单独承载筛选与试拍动作。
  防护：以后同一专用工作台的相邻步骤，如果都属于同一产品流程，顶部信息架构必须保持同一语法；禁止一个步骤像工作台、另一个步骤像后台控制台。

- 问题：商品棚拍 Step4 的候选卡如果继续用整块 pending/failed 遮罩，会把图片本身吃掉，看起来像状态列表，不像交付墙。
  根因：状态反馈被设计成“覆盖整张卡片”，优先级高于图片本身，导致用户先看到状态层，而不是候选内容。
  修复：把 pending / failed 改成底部轻量状态条，保留顶部标签和状态 badge，让卡片先是候选图，再是状态说明。
  防护：以后结果墙里的状态反馈默认采用“轻量附着”原则；除非阻断交互，不得再用整块遮罩覆盖候选卡。

- 问题：用户要求“整体风格完全复刻静态页”时，如果只改某个工作台，首页、任务中心和全局顶栏仍保持后台白壳，用户看到的第一印象就会判定“完全没变化”。
  根因：之前把静态稿理解成单页参考，而不是全局壳层基线，导致首页、任务中心、工作台分别使用三套视觉语法。
  修复：把全局 `TopBar`、页面容器和移动底栏改成静态稿的深色固定顶栏语法；通用 `card / btn / badge / status-banner` 同步切到深色金色体系；移除常规页面的全局左侧栏，改为“顶栏 + 内容页自己承载导航”。
  防护：以后用户明确说“整体风格完全复刻参考稿”时，默认先核对全局壳层，再改单页；如果 `TopBar / page shell / tasks page` 没一起变，禁止宣称已对齐参考稿。

- 问题：静态稿没有全局左侧栏，但项目仍保留“顶部 + 左侧后台栏”的旧信息架构时，无论怎么换色，都会继续像传统后台，不会像静态稿。
  根因：把左侧栏当成长期基础设施，没有判断它是否已经和参考稿的信息架构冲突。
  修复：常规页面壳层改成单列内容容器，不再把 `AppSidebar` 作为默认布局的一部分。
  防护：以后复刻外部参考稿前，必须先判断“导航承载层”是否一致；如果参考稿是顶栏主导航，禁止保留旧侧栏再做局部换肤。

- 问题：即使全局顶栏已经切到静态稿语法，如果资产中台和积分页仍保留旧的“工具后台摘要卡”写法，演示时会出现首页像静态稿、内页像旧后台的断层。
  根因：之前把资产中台和积分页当成功能页，没有把它们纳入“整体风格完全复刻”的范围。
  修复：为资产中台和积分页补了统一的 `page-hero-card / page-content-card / page-tab-head / page-tab-strip` 结构类，保证这些常规页也使用同一套深色内容页语法。
  防护：以后只要调整全局壳层，必须同步检查首页、任务中心、资产中台、积分页四类页面；任一页面仍保留旧后台页头，视为整体风格未完成。

- 问题：即便切成深色顶栏，如果导航、账号、积分这些文字仍在窄宽度下按字换行，页面会立刻从“静态稿风格”退回成“拼出来的后台”。
  根因：顶栏只是换了配色，没有把文字折行、布局压缩和信息减量当成一等问题处理。
  修复：把顶栏改成单行紧凑导航，移除冗余首页按钮，收成“品牌 / 导航 / 搜索 / 任务入口 / 账号 / 积分 / 退出”的一行结构，并强制品牌、导航、chip 不换行。
  防护：以后评估全局顶栏是否达标时，必须先看三个点：是否单行、是否折字、是否有重复入口；这三项任一不满足，就不能进入演示验收。

- 问题：首页如果继续保留“运营看板式堆卡片”的组织方式，即使颜色变了，也不会像静态稿的“工具入口页”。
  根因：首页之前优先承载指标和列表，没有先回答“用户打开首页第一步要做什么”。
  修复：把首页重组为“暗色 hero + 优先任务 + 样片广场 + 图片工具 + 视频工具 + 套餐 + 最近任务”的顺序，主 CTA 固定为进入商品棚拍，二级 CTA 固定为进入资产中台。
  防护：以后首页改版必须先判断它的角色是“入口页”还是“看板页”；如果是入口页，主视觉、主 CTA、工具分流优先级必须高于统计卡和列表。

- 问题：资产中台首屏如果直接从筛选 tabs 和列表开始，会继续像“素材后台”，看不出它为什么独立存在。

  修复：把资产中台首屏收成“资产操作台 hero + 当前优先任务 + 任务/素材/样片三视图”，并在任务视图前置“先处理最值得推进的任务”。
  防护：以后任何中台页都必须先回答“这个页面相对首页多提供了什么控制能力”；如果首屏只有筛选器和列表，默认视为结构未完成。

- 问题：任务中心如果只有创建表单和任务列表，虽然功能齐，但它不会像静态稿那样明确表达“先处理阻塞，再继续最近任务”。

  防护：以后任务中心必须至少具备两层语义：创建入口和任务决策；若只剩表单或只剩列表，不能算可演示的任务中心。

  修复：资产中台首屏样片区改成优先使用 `image_url / preview_image_url`，没有稳定地址时直接回退到静态占位，不再把本地预览路径用于 hero 样片位。
  防护：以后任何首页/hero/首屏样片位都不得依赖本地媒体路径；首屏展示位必须只用稳定公网 URL 或设计占位图。

- 问题：用户管理首屏默认落在“异常账号”筛选时，如果异常数量为 0，页面会直接显示空列表，演示时像数据没有接上。

  修复：用户管理在加载完成后会优先落到“异常账号 / 待处理 / 全部账号”中第一个有数据的视图，并在空筛选下提供“一键查看全部账号”。

  根因：一边保留 hero 内主指标，一边又把通用看板统计整块搬进首屏，造成语义重复。
  修复：首页 hero 改成“一套主指标 + 一排辅信息 + 状态提示”，不再重复堆两层统计卡。

- 问题：常规内页在顶栏下单独露出一条 `首页 / ...` breadcrumb，会立刻暴露旧后台结构，和静态稿的一体化内容页冲突。

  防护：以后全局壳层改造时，必须检查顶栏下是否还残留“单独一行的路径文字”；如果有，视为旧后台结构未清理完。

- 问题：即使全局按钮体系已经统一，如果商品棚拍工作台继续用自己的内联 `gold/dark` 按钮配色，演示时仍会像“独立主题页”，和首页、任务中心割裂。
